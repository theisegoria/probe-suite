# Jeep test drive: can the model make physics work, not just cite the API

The model writes one self-contained C++ source file. When run, it has to
cook the supplied terrain into a PhysX triangle mesh, build a four wheeled
vehicle to a written specification, spawn it, let it settle, and then drive
it through five waypoints over a ramp and a cross slope without rolling it.
Everything the scorer sees is a CSV of the trajectory the program wrote.

This is a different question from the geometry benchmark. There, the model
writes everything and the standard library is the only crutch. Here it is
working inside somebody else's large, versioned, badly documented API, and
the failure modes are the ones that make graphics and simulation work hard:
a parameter that is nearly right, an axis convention taken from the wrong
snippet, a controller that is stable in a straight line and not on a slope.

## What is supplied

```
assets/terrain.obj   2756 vertices, 5250 triangles, generated by harness/make_assets.py
assets/jeep.obj      the body, for the picture only. The physics uses the dimensions
```

The course runs along +z, with x lateral and y vertical, which is the
convention PhysX's own vehicle snippets use. There is a ramp between z = 26
and z = 38 peaking about 1.4 m, and a cross slope between z = 48 and z = 62
that will roll a vehicle taken too fast.

The harness supplies the include paths, links the seven PhysX static
libraries, and compiles in NVIDIA's own snippet vehicle helpers, so
`snippetvehicle::EngineDriveVehicle` and its friends are available. A model
may use them or build the component sequence itself. What it may not do is
read NVIDIA's JSON vehicle data: the numbers are in the prompt, and the
JSON is not shipped with the task.

## The ladder

Rungs are strictly ordered, so the number says which mistake was made:

```
1  compiles
2  runs without crashing
3  writes a parseable trajectory
4  the vehicle is stable at rest
5  the vehicle responds to its controls
6  it completes the course
7  it completes upright, in bounds, and inside the time budget
```

Rung 4 is where most of the API knowledge actually lands. A vehicle that
sinks, slides, or is launched at spawn has a suspension or a mass problem,
and that shows up in two seconds of simulated time before anything is
driven. Rung 5 separates a vehicle that is assembled from one that is
wired: throttle reaches the wheels, steering reaches the front axle. Rung 6
is the driving, and rung 7 is doing it in one piece.

## Verified, not assumed

```
./probe jeep selftest
```

Eight mutants of the reference solution, one per rung, each a plausible way
a real submission goes wrong:

```
ok    unmodified reference               rung 7 (expected 7)
ok    does not compile                   rung 0 (expected 0)
ok    compiles but exits non zero        rung 1 (expected 1)
ok    writes no trajectory               rung 2 (expected 2)
ok    spawned too high, still falling    rung 3 (expected 3)
ok    never applies throttle             rung 4 (expected 4)
ok    steers the wrong way               rung 5 (expected 5)
ok    gets round, but far too slowly     rung 6 (expected 6)
```

The reference earned its keep here too, twice. Its first run drove straight
through the terrain and fell for ninety seconds. The vehicle was fine: the
terrain grid was wound clockwise seen from above, so its triangle normals
pointed down, and PhysX culls backfaces in mesh raycasts. The suspension is
raycast, so the ground was invisible to it. The generator now emits the grid
counter-clockwise, and `harness/make_assets.py` says why in a comment.

The second was subtler. The reference reported five of five waypoints and
the ladder scored four, because the program broke out of its loop the moment
it arrived and never wrote the arriving tick. The trace is all the scorer
sees, so a finish that is not in the file did not happen. The task now says
so explicitly, and the reference writes the row before it stops.

Both of those are bugs a benchmark would otherwise have blamed on every
model that ran it.

## What the feedback carries

The trajectory, not a picture. How many ticks, how far, top speed, start and
end position, maximum tilt from upright, total heading change, and how many
waypoints were reached out of how many. It states what failed and by how
much, and never how to fix it.

## Running it

```
./probe jeep selftest                       # prove the ladder discriminates
./probe jeep run --model paste --task jd-01 # administer
```

## Requirements

A built PhysX 5. On Linux and Windows, use NVIDIA's own presets. On Apple
Silicon, upstream does not build at all, so this repository ships an
adaptor:

```
adaptors/physx-apple-silicon/build.sh
```

It clones PhysX, applies the patch, builds, and then compiles and runs a
smoke test that checks the vehicle sprung mass solver against a hand
calculation, because a build that produces libraries is not the same as a
build that produces correct ones. The patch is six changes: a
`PxHighestSetBit` overload for `size_t` on Darwin, NEON vector intrinsics
enabled for Apple, three NEON splat templates routed to the working
specialisations, an FPCR path for flush-to-zero in place of an x86 header,
and a binary platform tag for macOS arm64.

Set `PROBE_PHYSX_ROOT` to the `physx` directory of your own checkout, and
`PROBE_PHYSX_LIBDIR` if you want a specific build. Otherwise the harness
looks in `engines/PhysX` and finds the libraries itself.
